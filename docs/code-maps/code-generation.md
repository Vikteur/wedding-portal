# Code map: code generation

Decided in architecture-conventions §4 (line 232) and built in TASK-2.3: task `openApiGenerate` in `rekord-adapter`, OpenAPI Generator 7.25.0 pinned in the version catalog (`gradle/libs.versions.toml`). The task sets `cleanupOutput`, so each run empties the output and a tag or schema the spec no longer has leaves no stale type. Output lands in `rekord-adapter/build/generated/openapi/src/gen/java`, wired as a source root of `main`. Every compiling run needs `-Pcontract.spec=<rekord-contract checkout>/dist/openapi.yaml` (CI passes `contract/dist/openapi.yaml`). The contract tag in use is `rekordContractTag` in `gradle.properties` (v0.2.0 since TASK-2.4); CI reads it with `contract-pin.sh` and checks that tag out into `contract/`. `CiContractSpecTest` fails when a CI job that starts the application lacks the pin, the checkout or a `-Pcontract.spec` pointing into it.

Generated code is never edited or committed; a wrong shape is fixed in the contract (P4). A red build on regenerated but unimplemented interfaces is the expected start of a contract feature.

`CiContractSpecTest` treats as starting the application every Gradle run that starts a task other than a diagnostic or `clean`, and every image build. It fails closed on what it reads, which is the `run:` lines of every workflow and the root `Dockerfile`; it does not read what a step calls into (a script such as `./scripts/build.sh`, a `make` or `npm` target) or the `build:` section of a compose file, so a Gradle run behind one of those is not seen. It reads these run shapes: prefixes (`sudo`, `env`, `bash`, `time`, ...), the wrappers `timeout`, `nice` and `xvfb-run` (not exhaustive: a wrapper it does not know in front of the Gradle wrapper is refused), the shell keywords `if`, `then`, `elif`, `else`, `do`, `while`, `until` and `!`, `gradlew.bat`, `gradle`, either of them under a path, commands joined by `&&`, `||`, `;`, `|`, `&` or a line break, `#` comments (where a word starts, outside quotes), a Dockerfile `RUN` in shell and in exec form (any case; an exec form reads as its shell form, so `["sh", "-c", "./gradlew build"]` is checked), and `docker build` from the repository root, also behind the options docker takes in front of its subcommand (`--context`, `-H`, `--config`, `--debug`, ...). It exempts diagnostics, `clean`, commands that only mention the wrapper (`echo`, `printf`, `chmod`, `test`, `[`, `ls`, `cat`, `git`, `COPY`, `ADD`), and the setup actions it knows (`actions/checkout`, `actions/setup-java`, `actions/setup-node`, `actions/upload-artifact`, and `gradle/actions/setup-gradle` and `gradle/gradle-build-action` without `with.arguments`). It refuses everything else, and each refusal asks to extend the test: a command or Dockerfile line that names the wrapper or `gradle` in a shape it cannot classify, a docker option in front of the subcommand that it does not know, an image build from another context or Dockerfile, with `bake`, or with `docker compose build`, `up` or `run` (the compose file's `build:` is not read), any other `uses:` action, a reusable workflow, and a pin or contract checkout step whose `if:` the build steps do not share or that sets `continue-on-error`. Adding an action to a workflow therefore means adding it to `SETUP_ACTIONS` in the test or teaching the test to read it.
