## 2026-10-08 — TASK-5.7 cyclic cause chain

- Finding (proven on Quarkus REST 3.39.1 from thread dumps of the hung request and the library source, wedding-portal PR #38): an exception whose `getCause()` chain loops back hangs the worker thread. After `ErrorEnvelopeMapper` has answered, `org.jboss.resteasy.reactive.server.core.RuntimeExceptionMapper.mapException` (line 105) calls `logBlockingErrorIfRequired` (127), then `isBlockingProblem` (172), then `isKnownProblem` (187), which walks `getCause()` in `while (e != null)` with no visited set. The thread stays RUNNABLE at full CPU inside `isKnownProblem`, and no response is written. The catch-all had already logged its one line, so the log alone looks healthy. The loop is the framework's post-mapper logging and not our mapper: `RedactedCause` already cuts cycles. It runs for every exception, whichever mapper answered.
- Guard (owner approved 2026-10-08, logging STOP): `RedactedCause.of` answers an argument that already is a `RedactedCause` as it is. `AcyclicCauseInterceptor` (binding `AcyclicCause`, `@Priority(PLATFORM_BEFORE)`, so outermost) rethrows `RedactedCause.of(e)` only when the `getCause()` chain of what a resource method threw loops back (visited set by identity). Any other exception is rethrown as the same instance and a normal return passes through. The catch-all therefore logs what it logged before: one ERROR line, logger `ErrorEnvelopeMapper`, message `Unhandled exception`, no parameters, class names and frames only; the copy is logged as it is, not copied again. A cyclic chain answers the `error-unhandled-500` fixture byte for byte.
- Binding: `BindAcyclicCauseToResources`, a CDI build compatible extension registered in `application/src/main/resources/META-INF/services/jakarta.enterprise.inject.build.compatible.spi.BuildCompatibleExtension`, adds `@AcyclicCause` at build time to every concrete class that carries `@Path` or inherits it from a superclass or an interface. The real resources inherit it from the generated `*Api` interface, so a check for `@Path` on the class alone would miss all of them. It lives in `application` because the resources sit in `rekord-adapter`, which must not depend on application classes. ArC in Quarkus 3.39.1 applies it, also to classes of the adapter's Jandex index; no dependency was added. Nobody writes the binding by hand and a resource added later is guarded by itself.
- Tests: `AcyclicCauseInterceptorTest` and `RedactedCauseTest` (behaviour), `AcyclicCauseBindingIT` (the interceptor resolves for the binding, and every bean with `@Path` on its class, a superclass or an interface is served through an ArC interceptor subclass), `ErrorEnvelopeMapperIT` with the probes `/cyclic-cause` (`@Path` on the class) and `InterfaceProbeApi`/`InterfaceProbeResource` (`@Path` on an interface, like every real resource). Both probes have socket timeouts, so a regression fails with the name of the looping `RuntimeExceptionMapper` method and not as a build that never ends. `ErrorEnvelopeProbeResource.chain(boolean)` carries the same finding in its comment.
- Residual gaps. (1) Only an exception thrown from a resource method is covered. A cause cycle raised in a request or response filter, a body reader or writer, a parameter conversion, or any other code the invoker runs outside the resource bean still hangs the thread. (2) A failure delivered later through a `Uni` or `CompletionStage` is not seen, because the interceptor wraps the call that returns the promise. (3) A sub-resource class with no `@Path` on itself or on an interface is not bound. (4) Trade-off, accepted by the owner: a `RekordException` or `WebApplicationException` whose chain loops back answers 500 `UNKNOWN` and logs one ERROR line instead of its own status, because the copy is neither (pinned by `AcyclicCauseInterceptorTest`). No resource in the application builds such a chain today. Nothing was reported or fixed upstream.
- If a later Quarkus REST visits each cause once in `isKnownProblem`, the interceptor, `AcyclicCause`, `BindAcyclicCauseToResources`, its services file and the interface probe can go; check by deleting the services file and running the two `ErrorEnvelopeMapperIT` cyclic tests. `RedactedCause.of` can stay idempotent either way. The TASK-5.2 bullet on the catch-all log line is not wrong: the cyclic case logs the same line.
- Review follow-up, 2026-10-08 (PR #38 review, appended; nothing above is edited). Correction: the Guard bullet says the interceptor is outermost "so it sees what validation, security and transactions throw too"; drop "security". The review found that Quarkus REST checks endpoint security before it calls the bean, so a cause cycle raised there is out of the interceptor's reach, like a filter's (gap 1), and it is not tested. Validation and transactions run inside the interceptor chain and stay covered: `ErrorEnvelopeMapperIT` now pins that the guard is outermost, with a test-only interceptor (`CyclicChainInterceptor`, `LIBRARY_BEFORE`, behind the guard's `PLATFORM_BEFORE`) that throws the cyclic chain on the `/cyclic-from-interceptor` probe; binding the guard innermost turns it red. Also from that review, so the Tests bullet is read with it: `BindAcyclicCauseToResources` now publishes the classes it bound as the `AcyclicCauseBindings` bean (CDI Lite `@Synthesis`), and `AcyclicCauseBindingIT` holds every resource bean against that set, not only against "has an interceptor subclass", which a resource with bean validation or a transaction also has; `SuperclassProbeBase`/`SuperclassProbeResource` pin a `@Path` on an abstract superclass; `RedactedCause` keeps the class name of a copy nested as a cause or suppressed exception (log line count, message and class-names-only are unchanged); a super type missing from the build classpath fails the build naming the class.

## 2026-10-08 — TASK-6.1 route guard and the security extension

- Supersedes the TASK-5.2 bullet "New dependencies in `application/build.gradle.kts`: `io.quarkus.security:quarkus-security` and ..." (that bullet stays as written). The security dependency is the Quarkus extension `io.quarkus:quarkus-security` (BOM-managed, 3.39.1). The library line alone (`io.quarkus.security:quarkus-security`) gave no `io.quarkus.security` capability, so Quarkus REST enforced no `@Authenticated` (PR #31 review M4). Both lines are now declared, and both stay on purpose: the library line (`io.quarkus.security:quarkus-security`, the exception API jar) was added by TASK-5.2 (commit 6011c4f) because `ErrorEnvelopeMapper` in `application` imports `io.quarkus.security.AuthenticationFailedException` and `UnauthorizedException` directly, and the extension line is what turns enforcement on. Only `RouteGuardIT` catches the removal of the extension line, because `RouteGuardTest` reads class files and never starts Quarkus. From now on `@Authenticated`, `@RolesAllowed`, `@DenyAll` and `@PermitAll` are enforced on resources in every profile (owner decision D1).
- `RouteGuardTest` (fast set) reads class files, not CDI beans (a deviation from rekord-api, which walks beans in a `@QuarkusTest`): the routes of the interfaces directly in `app.rekord.api` with a floor of 60 (a floor, not an exact count, so a contract bump needs no edit here); the seven-entry allow-list `RouteGuard.PUBLIC`, pinned exactly so a widening is a visible decision, with stale entries (renamed or removed operations) named; every concrete implementation of a generated interface must carry `@Authenticated`, `@RolesAllowed`, `@PermitAll` or `@DenyAll` on the implementing method or class, and annotations on the generated interface are not counted (BR-OPS-22). A class-level annotation counts only on the class that declares the implementing method, so an annotation on a subclass does not guard a route implemented in its unannotated superclass. `RouteGuard.overGuarded` names an allow-listed route whose implementation carries an access annotation (it would refuse a visitor), and `RouteGuard.resourcesOutsideTheGuard` names a production class that serves routes without implementing a generated interface (a loose `@Path` class, or routes taken from an interface outside `app.rekord.api`). Routes are named `Api#method`, so overloads count once and one allow-list entry covers them all. Not seen: routes that are not JAX-RS classes in the class directories of the modules (a Vert.x `@Route` or `Router` handler, a route from an extension or a dependency jar, a static resource), and which roles an annotation names.
- `RouteGuardIT` and the probe resource `RouteGuardProbeResource` under `/api/test-only/route-guard/` (`authenticated`, `roles-allowed`): without a session they answer the `error-not-signed-in-401` fixture byte for byte and the body never runs; `GET /api/health` still answers 200 `{"ok":true}`.

## 2026-10-08 — Follow-up tickets are recorded as JSON, not in the backlog

- Owner decision, 2026-10-08 (chat): work a review or a retro leaves open is no longer suggested in chat or started as a Backlog.md ticket. Each item becomes one JSON file in the weddingapp umbrella repo, under `docs/follow-ups/<epic folder>/`: one folder per epic (`TASK-2-P0-E02`, for example), and `no-epic` for a ticket without a parent epic.
- Each file names the original ticket (id and title), the epic, why the item was deferred instead of fixed in the review phase, the impact (HIGH, MEDIUM or LOW) and a priority score from 0 to 10. The field list, the impact levels and the scoring rubric are in the umbrella's `docs/follow-ups/README.md`, and the shape is `docs/follow-ups/follow-up.schema.json` there.
- Only a follow-up scoring above 7 may be added to Backlog.md. The owner reviews the rest later, because a ticket planned later in the backlog may already solve some of them.
- Fix in the pull request first. A follow-up needs a reason it could not be fixed in the review phase: it is outside the ticket's scope, it needs an owner decision or a STOP approval, it belongs to another repo, or it is larger than the ticket.
- This replaces proposing follow-ups in a review's "Suggested Follow-up Issues" or a retro's `Actions` for the owner to ticket. Those sections still list them, and the coordinator turns each one into a follow-up file after the merge.
- Owner decision, 2026-10-08 (chat), on the same day: follow-ups about the agentic framework are kept apart from product gaps. Each file has a `category`. An agentic follow-up goes to `docs/follow-ups/agentic/<category>/`, with one subfolder each for `workflow`, `skill`, `instruction`, `hook`, `agent` and `script`. A product follow-up (`code`, `ticket` or `repo`) stays under `docs/follow-ups/<epic folder>/`. Each file also has `ownerDecision`, true when the item cannot start without an owner decision or a STOP approval.
